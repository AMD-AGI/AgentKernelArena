# Qualify a Magpie serving task for AgentKernelArena

The Magpie workload catalog contains serving benchmark recipes for a wide range
of models, backends (SGLang, vLLM, ATOM), and scenarios. Qualifying a recipe
turns it into a reproducible Arena serving task: you bind it to a pinned runtime,
prepare immutable assets, and confirm that the unmodified baseline passes all
correctness and calibration gates before any optimization agent runs.

Use this workflow when the two maintained tasks
(`e2e/qwen3_0_6b_sglang`, `e2e/qwen3_next_80b_sglang`) don't cover the model or
workload you need. See [Run end-to-end serving tasks](e2e-kernel-tasks.md) for
running those maintained tasks without additional setup.

**When this workflow is complete:** the task has a framework-finalized validator
PASS and passing baseline calibration on the locked runtime. It can be selected
by any optimization run that specifies the same GPU architecture.

## Prerequisites

- Clean, pinned checkouts of
  [Magpie](https://github.com/AMD-AGI/Magpie) and
  [InferenceX](https://github.com/SemiAnalysisAI/InferenceX) at the revisions your
  runtime profile will reference. Moving branches and tags are rejected — use
  full commit identifiers.
- A GPU host running the AgentKernelArena Docker runtime on the target
  architecture. See [Install AgentKernelArena](../install/install.md).
- Python with PyYAML on the host (outside Docker). The steps below create an
  isolated venv.
- For models not already downloaded: access to the model weights at the exact
  revision you will declare in the runtime profile.

## Step 1: List the catalog

Inspect the available recipes without GPU access:

```bash
python3 -m src.magpie_catalog list
```

Each entry shows the recipe ID, backend, scenario, and model. The maintained
catalog is at `tasks/e2e/magpie/catalog.json`. To refresh it from a clean
upstream Magpie checkout:

```bash
python3 -m src.magpie_catalog refresh --checkout ../Magpie
```

Catalog refresh preserves original recipe bytes and hashes. It does not change
existing runtime bindings or task directories.

## Step 2: Build the runtime profile

The runtime profile is private maintainer input — it is never generated by an
optimization agent and is not refreshed during a run or resume. Create a JSON
file (outside the repository) that declares:

- **`image`**: an immutable registry digest; `gpu_arch`, `gpu_count`, and the
  actual `model_architectures` class names from the model's configuration file.
- **`model`**: the recipe's model ID and exact full commit revision. For
  host-local models, also supply an explicit `source_model_alias`.
- **`correctness`**: the numerical reference policy and baseline-calibrated
  tolerances, sample counts, and generation lengths. See
  [Correctness policies](#correctness-policies) below for the supported types
  and how to calibrate them.
- **`client_runtime`**: how the benchmark client runs. Use
  `{kind: image, executable: /opt/client/bin/python}` when the pinned image
  already supplies the native client and all its dependencies. Otherwise use
  `{kind: archive, asset: client-python.tar.gz, executable: python/bin/python3.12}`
  and declare the archive in `assets` with its SHA-256 and either a public
  HTTPS URL or `source: provided`. Pass `--asset-file client-python.tar.gz=PATH`
  to `src.prepare_serving_runtime` for offline-supplied files.
- **`server_seed`**: a fixed seed for SGLang. If the upstream recipe has an
  explicit seed, it is preserved; otherwise, task materialization freezes
  `1729` before either role starts. A conflicting explicit seed is rejected.
- Optional fields: `limits` (see [runtime limits](../reference/e2e-reference.md#runtime-limits)),
  `measurement_num_prompts`, `server_topology`, `runner_type`.

### Correctness policies

Choose one policy before qualification and do not change it after search begins.

- **`transformers_fp32`** — Compares log probabilities against an independent
FP32 Transformers reference. Requires the FP32 reference model to fit the
evaluation hardware.

- **`production_numerical`** — Uses fresh original-server prefix comparisons and
teacher forcing of actual candidate continuations, without imposing one answer
dataset on every model. Calibrate `max_abs`, `mean_abs`, and `p99_abs` bounds
separately for input-prefix and decode logprob comparisons. Optionally declare
`decode_logprob_tolerances` for independently calibrated decode bounds;
without it, the input-prefix bounds apply to decode as well.

- **`production_quality`** (for FP8 models) — Also requires a frozen
`quality.json` and quality policy. The fixed answer-accuracy subset is an
additional regression gate; its minimum accuracy, allowed drop, sample count,
and answer parser are task-owned and cannot be changed by an agent.

Calibrate tolerances on repeated unmodified original-server runs before search
begins. A passing calibration is a finite check, not a variance estimate. Do not
adjust tolerances after seeing a candidate; do not rerun until a convenient
score appears. Verify bounds on a held-out original run.

For ATOM images, choose either `production_tokens` with `token_match: exact`
or `transformers_tokens` and declare the policy before qualification. The
policy is protected and included in measurement identity.

## Step 3: Bind the catalog entry

Run the bind command from clean, pinned Magpie and InferenceX checkouts:

```bash
python3 -m src.magpie_catalog bind \
  --id <recipe-id> \
  --profile ../runtime-bindings/runtime-profile.json \
  --magpie ../Magpie --inferencex ../InferenceX \
  --output ../runtime-bindings/<recipe-id>.json
```

Binding paths in a run config are relative to the run-config file, not the
task directory. Keep private bindings outside the checkout. For a run config
under `example_configs/`:

```yaml
tasks:
  - e2e/magpie/<recipe-id>
serving_runtime:
  bindings:
    e2e/magpie/<recipe-id>: ../../runtime-bindings/<recipe-id>.json
```

See the maintained SGLang example in
[`example_configs/e2e_magpie_qwen3_next_80b_validator_mi355x.yaml`](https://github.com/AMD-AGI/AgentKernelArena/blob/main/example_configs/e2e_magpie_qwen3_next_80b_validator_mi355x.yaml).

## Step 4: Prepare assets

Create an isolated host-side Python environment and run asset preparation
against your validator config:

```bash
python3 -m venv ~/.local/share/aka-serving-venv
~/.local/share/aka-serving-venv/bin/python -m pip install PyYAML
export AKA_SERVING_PYTHON=~/.local/share/aka-serving-venv/bin/python
"$AKA_SERVING_PYTHON" -m src.prepare_serving_runtime \
  --config example_configs/<your-validator-config>.yaml
```

For offline-supplied assets, pass `--asset-file <name>=<path>` for each
declared `source: provided` asset. The host acquires and content-verifies all
assets; each clean action extracts them locally before measurement. Missing
assets fail before GPU work starts.

The asset cache defaults to `~/.cache/aka-serving`. For shared-storage
clusters, explicitly set `AKA_SERVING_TASK_CACHE`, `AKA_SERVING_CACHE`, and
`AKA_SERVING_ARTIFACT_ROOT` to task-owned storage before preparation.

## Step 5: Validate and qualify the baseline

Run the validator to confirm all checks pass on the locked runtime:

```bash
make docker-run CONFIG=example_configs/<your-validator-config>.yaml
```

Qualification requires a framework-finalized task-validator PASS on the locked
GPU runtime. CPU regression tests alone do not qualify an e2e task. The
validator runs baseline compile, correctness, and calibration checks.

A failing baseline calibration blocks search. Resolve failures before
proceeding; do not adjust tolerances to pass a failure. A resume reuses the
same prepared contract and existing session checks — it does not regenerate a
baseline from edited candidate code.

After a PASS: the task is ready for optimization runs. Use
`make docker-run CONFIG=example_configs/<your-optimizer-config>.yaml` with any
supported agent. See [Run end-to-end serving tasks](e2e-kernel-tasks.md) for
the optimization workflow.

## Multimodal and AgentX tasks

### Media workloads

Multimodal profiles additionally declare a `request_manifest` with:

- `dataset_sha256`: SHA-256 of the complete input dataset.
- `input_lens` and `output_lens`: exact per-request lengths from the pinned
  native client's unmodified preparation run.

Set `correctness.media_sha256` to the JSON bytes of the protected
`inputs.media_checks.json` (image-bearing chat requests with inline data URIs
and fixed decode lengths) and use `production_serving` as the correctness
policy. Both numerical/logprob and no-logprob paths must match fresh
original-server continuations. Media models with divergent normal continuations
need a separately qualified numerical policy; text-only probes do not qualify
image kernels.

### AgentX trace workloads

AgentX profiles declare the resolved canonical `agentx.launch_spec` (literal
`argv`, `env`, `health_path`) and its `recipe_fingerprint`, plus
`agentx.client` captured from the pinned native replay preparation.

Declare the exact AIPerf source in `dependencies` and offline trace files in
`assets` as relative names with SHA-256. Use `{model}`, `{client}`, `{root}`,
`{port}`, and `{assets}` placeholders for evaluator-owned paths and endpoints.

The `request_manifest` fixes `dataset_sha256`, `duration_s`, and trace turns.
If `input_tokens` counts the native loader's reconstruction budget rather than
wire tokens, bind `input_token_policy: native_reconstruction` before
qualification — this policy is protected and included in measurement identity.
Keep the default exact policy when the manifest describes complete wire requests.
Never apply this policy to excuse modified client inputs or truncated requests.

Throughput uses the native observation start and end timestamps, including
initial idle time and terminal grace and drain time. Native aggregate
completion and error counters must agree with completed records; missing rows
and context-overflow skips cannot silently change the measured workload.
